# Native Pivot import pipeline

A stopped, untransferable or timed-out import worker rejects its outstanding requests and releases its resources. The next user import starts a new worker; failed work is never automatically repeated. Events arriving from a replaced worker cannot resolve or reject the new worker's requests. Worker errors preserve only allowlisted module/line diagnostics across the boundary.

Pivot files are decoded by the Pivot codec, `engine/crates/styk-piv` compiled to WebAssembly, which runs in a worker of the editor page on every platform (`src/codec-web-worker.mjs`, see [Pivot files and the codec service](engine/formats-piv.md)). It answers what the original Python decoder answered, with the same editable report schema; the Python codec in `codecs/` and `backend/` is kept only as its development test oracle. Native v5 imports avoid constructing and serializing a second complete pose inventory: the codec validates the frame table, transfers its original bytes, and the import worker builds the editable JavaScript objects once. Legacy PIV, STK and project JSON use the full decoder and acknowledged JSON transport.

The import worker reaches the codec over a MessagePort (`src/codec-request.mjs`), one port per job, with the request and response shapes of the former HTTP service. Requests from every job join one queue in the codec worker (`src/codec-web-shell.mjs`). Cancelling a job sets a shared flag (a `SharedArrayBuffer`, on cross-origin isolated pages) that the codec polls at its checkpoints, so the running request stops and the worker keeps its imported originals; without isolation the busy worker is stopped and the next request starts a fresh one. The web build embeds each Pivot import's verified original in its document; the desktop app and the development server keep it leased in the codec, as the desktop service did. On the desktop the main process lists the sample files and reads one (`desktop/samples.cjs`), and a sample opens as an ordinary import of its bytes.

Legacy JPEG resources retain their declared absolute record endpoint. The codec (`styk-piv` `piv/image_stream.rs`, after `codecs/image_stream.py`) validates JPEG segments and entropy markers through EOI and exposes only the actual image to the browser; padding inside the resource remains in the original source. No record or frame boundaries are inferred from image marker searches.

Missing v5 sprite data preserves the figure, resource slot, anchors, poses and joins. Empty image records and an end pointer left at its own offset become a canonical transparent 1×1 PNG with `missing_image_data` provenance. An omitted pointer is recoverable only for the final image in a figure with implicit draw order, no text or outline, and an immediately valid zero-polygon/name suffix. The remaining figure table, all frames and the trailer must still validate before publication. Other invalid pointers and truncation remain errors. `piv_missing_images` records affected definitions and offsets, and import notes tell the user which artwork is absent. Edited PIV exports write valid transparent images; unchanged exports and native source-bearing saves retain the original bytes. Regression coverage: `styk-piv`'s tests, `backend/test_piv_media_recovery.py` (the oracle) and `tests/piv-media.browser.mjs`.

The internal `application/vnd.stykanimate.piv-frames-v1` response contains `STYKPIV1`, a little-endian JSON-header length, the decoded definition/media/header document with an empty `keyframes` array, and the exact validated native frame table. `nativeFrames` records the original byte offset and payload extent. This is a transfer format between the codec and the import worker, not a replacement for `.piv` or `.styk` files.

The codec validates native frames without allocating pose dictionaries (`styk-piv` `piv/frames.rs`): bounds, numeric, topology, reference, order and continuity checks, as `backend/fast_decode.py` and the optional C++17 scanner `native/piv-frame-scan.cpp` did for the Python codec (both now serve only the oracle). `/api/health` reports `nativeFrameScanner: "rust"`.

The import worker parses the compact JSON header, sends it in acknowledged batches of at most 4 MiB, and transfers the native frame buffer without copying. `.styk`/`.stkz`/`.stykmov` files do not round-trip through the service at all: the worker opens container versions 1 and 2 (plus legacy JSON) with `styk-formats` in its own instance of the codec module (`src/native-file-codec.mjs`), which verifies section checksums, admits every marker, applies the document rules and checks the embedded original source fingerprint, and the worker materializes the binary sections back into ordinary editable arrays and strings (`restoreLifted`, `src/document-lift.mjs`). `src/import-wire.mjs` materializes native fields and ordinary editable arrays in cooperative tasks with a 3 ms scheduling target. Long pose arrays also yield internally. It publishes `keyframes` only after the complete table succeeds. Cancellation, disposal, malformed input and superseded requests cannot publish a partial scene.

Wire/source limits and an estimated 2560 MiB (2.5 GiB) pose-inventory budget are separate checks. The latter accounts for frames, object records, pose scalars and joins before the corresponding allocations; it is an admission estimate rather than a measurement of JavaScript heap usage. The codec and the JavaScript materialization enforce the same estimate. Scheduler delays, garbage collection and individual native operations can exceed the target task duration.

The source cache retains the original compressed file and compact transfer representation. A caller requesting canonical JSON or native export obtains that representation lazily; the codec runs one request at a time. Original-byte export remains exact when the decoded scene is unchanged. `editor.loadAsync` then performs the editor's semantic validation and index preparation independently before one atomic document publication; see [EDITOR-IMPORT.md](EDITOR-IMPORT.md).

Correctness evidence includes every field and JSON property order in all 23 original native-v5 corpus reports, all 1,479 frames and 208,373 objects in the user's 17.18 MB Akane file, malformed/truncated/cancelled transfers, zero stored frames, lazy-cache concurrency, and exact unchanged native exports. Relevant tests are `tests/import-wire.test.mjs`, `tests/import-wire-review.test.mjs`, `tests/import-wire-akane.mjs` (the Rust codec's transport against the Python oracle's canonical decode), `tests/codec-engine.test.mjs`, and, for the oracle, `backend/test_import_wire_review.py` and `backend/test_fast_decode.py`. The parity replay (`engine/tools/piv/parity.sh`) compares the Rust codec's answers with the oracle's, including deterministic byte mutations, truncated inputs, signed UIDs and long join chains.

The source-stable one-process diagnostic in `artifacts/matched-app-interaction-cpp-async-clean-v1/report.json` measured cold import to first GPU completion callback at 2016.8 ms and warm import at 1699.1 ms on the tested Windows machine. A later readiness audit found that this first submission preceded the background texture: these values describe an incomplete first submission, not a complete visible imported scene. It opened the last stored key directly and passed both sets of 23 subsequent pose/pixel checks. The initial viewport was vertically offset by 13 pixels from the native benchmark, while the later pose trials used the exact matched transform. Remaining first-render tasks lasted 67/52 ms. These diagnostic results must not be compared directly with native Pivot's different Present-return endpoint or used as complete-scene import latency.

The subsequent source-stable actual Electron Akane diagnostic measured 2224.2 ms cold and 1640.9 ms warm from file change to the first complete-scene GPU callback. Both first submissions already had decoded media and the required texture-backed background. Initial rendering took 0.6/0.5 ms of CPU wall time with no primitive uploads; scene staging uploaded 1,746,816 bytes in three calls. There were no import main-thread long tasks of 50 ms or more. Retained batch pixels matched the old 615-upload path exactly, and both sets of 23 pointer mutations matched the independent renderer and all 15,697 native pose nodes within 0.000031 world units. This is one diagnostic pair on one Windows machine, with a correctness upload comparison before the gestures. It is not the final three-process timing run, a physical input/display measurement, or a direct speedup comparison with native Present return. Full phase timings, stable runtime hashes, screenshots and qualifications are in `artifacts/matched-app-interaction-atomic-diagnostic-v1/SUMMARY.md` and `report.json`.

Opening a project does not use this transport. The engine reads the file (or the document's JSON) on its own workers,
normalizes it as the editor's load does and keeps it; the editor receives a read view of it in slices
([engine/document.md](engine/document.md#opening-a-document)). The codec keeps the original of a Pivot file only to save it again
(`/api/source/keep`; the web build embeds it in the document). The transport above serves the imports that are not
opened as projects, such as a figure taken from a library file.
