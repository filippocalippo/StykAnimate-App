# Release history and shipping

## Authoring contract

`CHANGELOG.md` is the only authored source for new release notes. `desktop/release-info.json` (the offline What's new dialog) and `release-notes.md` (electron-builder and GitHub) are generated by `npm run release:prepare`. The public website reads published GitHub releases.

During development, put completed, user-relevant features and fixes in the single top `## [Unreleased]` section. These notes are public and written for people using the app. Omit private or internal-only changes, agent instructions, tests, refactors without observable effects, and build housekeeping. Keep necessary engineering context in internal documentation or commits; never expose private identifiers, paths, or diagnostic data in release notes.

Before adding a bullet, read existing pending notes and the relevant history. Update an existing bullet when completing the same feature, grouping related work by user-visible outcome. Write a concise, natural sentence about what users can do or what problem is resolved. For example, write "Fewer pauses when editing complex animations" rather than listing cache and worker changes. Include technical detail only when it helps users understand compatibility, limitations, or required action. Omit plans, unsupported performance claims, and repetitive implementation detail; not every code change needs an entry.

### Writing style

Release notes should read like a polished consumer app's changelog, not a commit log.

- One short sentence per bullet, two at most. Lead with the feature or the result: "Command palette: press Ctrl+P or F1 to find any command, setting, layer, figure or frame."
- Added: name the new thing and what it lets people do. Changed: say what is different now. Fixed: "Fixed …" followed by the problem people saw, such as "Fixed error messages appearing behind open dialogs." Performance: the effect people notice, such as "Older Pivot animations open several times faster."
- Mention a shortcut or where to find a feature at most. Do not walk through every button, option, color, edge case, or undo behavior; the app and the documentation cover that. When extending an existing entry, rewrite it to stay short instead of appending clauses.
- Never mention internals: rendering, GPU, workers, caches, textures, memory budgets, engines, file-format internals, code names, tests, fixtures, or regressions in our own tooling. Say "Smoother playback", not how it was achieved.
- Use correct grammar, sentence case, consistent spelling (color, not colour), and end every bullet with a period. Titles are short, plain phrases with no trailing period, and never all capitals.
- Before a release, read the whole section from top to bottom as someone using the app would, then trim, merge, and reorder until it is easy to scan.

Use `### Added`, `### Changed`, `### Fixed`, `### Performance`, `### Removed`, `### Security` in that order, omitting empty categories. Keep each bullet on one line, group related items, and put the most significant change first within a category. A release section has a unique `## [x.y.z]` heading, one plain-text title line, then its categories. Versions use numeric newest-first order, not lexical order. Only the top Unreleased section may be empty. Release headings identify the version being built; they do not themselves prove publication.

Validation rejects duplicate version headings, duplicate categories, malformed or unordered sections, empty releases, repeated entries after case/spacing/punctuation normalization, version mismatches, and stale generated notes. It checks repeated text across history too: a later regression must describe its distinct trigger and fix instead of copying an old entry. Semantic duplicates still require editorial review. Published history is preserved by review; the validator does not compare it against remote Git history.

The initial 0.5.5 section comes from existing release metadata, with overlapping feedback instructions consolidated. Earlier missing versions and publication dates have not been invented. Do not retroactively assign existing uncommitted application changes to a release without establishing their scope and verification.

## Prepare the next version

1. Start a release branch from a freshly fetched `origin/main` (for example `release/<version>`). Inspect the working diff, current package version, and existing release tags. Select the requested new higher version; do not reuse a published version.
2. Move all completed pending entries from Unreleased into one new highest version section, immediately below an empty Unreleased heading. Add a concise title. Move entries rather than copying them; leave older sections unchanged. Do not leave changes included in the release stranded in Unreleased.
3. Set that version in `package.json`, `package-lock.json` at the top level, and `package-lock.json` at `packages[""].version`. `npm version <version> --no-git-tag-version` can update these in a suitable checkout; review its diff.
4. Run `npm run release:prepare`, then `npm run changelog:check`. Preparation validates the entire history before writing and replaces each generated file through a sibling temporary file. It is deterministic and safe to rerun. An interrupted update of the two files is detected by the check; rerun preparation to repair it. Use one writer for release metadata at a time and reread after concurrent edits.
5. Review the new section for accuracy, semantic duplicates, omissions, and ordering. Confirm generated files contain only the newest version, excluding Unreleased and older history. Run `node --test tests/changelog.test.mjs`, `npm run check`, `npm run test:updates`, and relevant feature, browser, desktop, and performance checks. Run `npm run test:updates:desktop` for releases.
6. Commit the history, both package files, both generated files, and intended source changes together. Confirm all required files are saved in the reviewed diff. A generated file should never be fixed by hand. Open a release pull request against `main`; features and fixes are merged before it, never inside it. Subsequent development entries go only into Unreleased.

## Build and ship

Use `.github/workflows/desktop-release.yml` for the current runtime pins and coordinated Windows, Linux and browser verification. `docs/UPDATES.md` covers updates and public assets; `docs/DESKTOP-RELEASE.md` covers package verification and the local launcher marker. A feature implementation request does not imply publication authorization. An explicit release request authorizes its normal shipping steps; do not ask again without a concrete new blocker.

For a local Windows release, install the locked dependencies and build prerequisites described in those documents, then run:

```powershell
npm run changelog:check
npm run build:frame-scan
npm run build:vfw
npm run build:sidecar
npm run verify:sidecar
npm run build:video-encoder
$releaseVersion = (Get-Content package.json | ConvertFrom-Json).version
npm run dist:win -- --x64 --publish never "--config.directories.output=release/$releaseVersion"
$env:STYK_PACKAGED_RESOURCES = Join-Path $PWD "release/$releaseVersion/win-unpacked/resources"
$env:STYK_PACKAGED_EXECUTABLE = Join-Path $PWD "release/$releaseVersion/win-unpacked/StykAnimate.exe"
npm run verify:package
npm run test:desktop:packaged
npm run mark:release
npm run release:verify -- "release/$releaseVersion" --platform=win32
```

Check each command's exit status and stop on failure; PowerShell does not automatically stop after a failed native command. Build and verify Linux on its own host as described in `docs/LINUX.md`. Combine its AppImage and `latest-linux.yml` with the four Windows assets in `release/<version>`, then run `npm run release:verify`. The default verification and publisher require both platforms.

Releases are built only from commits on `origin/main`. For a coordinated candidate, merge the release pull request and run:

```bash
gh workflow run desktop-release.yml --ref main -f publish=false -f upload_draft=false
```

This retains private Windows/Linux assets, browser files and verification evidence for 30 days. It includes an actual installed Windows upgrade from the previous public release. No public draft or deployment is created. Before retaining anything, each platform verifies its versioned unpacked package against the source and staged runtimes, boots that executable, and exports and decodes videos from its startup scene; these checks need no private samples. The package hash manifest stays with the private evidence, and CI never synchronizes advancing source into the package. Review the successful run for that exact commit; old reports do not certify new bytes. If the candidate fails, fix it in another pull request and run it again; nothing is public until publication.

When publication is authorized, dispatch with `upload_draft=true` for a verified draft or `publish=true` to publish. A matching `v<version>` tag push also publishes automatically. Locally, `npm run release:publish` uploads the verified combined directory as a draft, and adding `--publish` publishes it. The publisher checks saved notes before any remote action and refuses to replace a public version. Only the fixed asset allowlist is uploaded. Deploy the browser editor from the verified commit, run its live checks, then refresh and deploy the website catalogue as documented in `docs/WEB.md` and `docs/website.md`.

After publishing, confirm the public tag, notes, Setup and Portable executables, Setup blockmap, `latest.yml`, Linux AppImage, `latest-linux.yml`, and `SHA256SUMS.txt`. Exercise the real update path described in `docs/UPDATES.md` and record evidence and any limits. Leave the release section frozen and Unreleased ready for new work. Report the version, release URL, verification performed, and remaining platform limits. Never report a draft or a failed upload as a shipped release.
